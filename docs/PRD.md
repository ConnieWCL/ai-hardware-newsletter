# AI 硬件情报 Agent · PRD

> 一句话定位：**一个为 AI 硬件求职者定制的每日情报系统**——多源采集、两级去重、LLM 结构化摘要、零服务器定时投递，日均成本 ¥0。
> 仓库：github.com/ConnieWCL/ai-hardware-newsletter　　公开存档：conniewcl.github.io/ai-hardware-newsletter　　文档版本：2026-08-31

## 1. 背景与问题

求职国内 AI 硬件方向期间，需要每天跟进产业动态。现成方案都不够用：机器之心、The Verge 等日报是**面向所有人的泛化内容**，缺产品视角（定价、定位、成本/功耗取舍），且信息过载——绝大多数个人情报系统死于第三周"未读 99+"。

同时，项目需承担第二个目标：作为**可展示的工程作品**。因此设计上刻意保留了每个环节的决策痕迹（见 `docs/ARCHITECTURE.md`），而不只是"能跑就行"。

**路径选择**：先用平台化工具跑两周做需求验证（栏目结构、信息密度、信源取舍），再自建工程化版本。前者验证"做什么"，后者解决"怎么做"。

## 2. 为什么必须用 AI

| 环节 | 规则/脚本能做吗 | 结论 |
|---|---|---|
| 采集 | 能（RSS） | 用代码，不用 AI |
| 去重 | 能（URL 规范化 + Shingle-Jaccard） | 用代码，毫秒级、零成本 |
| 相关性判定 | 勉强——关键词曾把"太空望远镜"因文中 `funding struggles` 判为融资新闻 | 规则做粗筛，LLM 做终判 |
| 结构化摘要 + 中文重写 | 不能 | **必须 LLM** |
| 产品经理视角点评 | 不能 | **必须 LLM** |

**核心设计原则：AI 只用在规则做不好的环节**。采集、去重、事实校验全部用确定性代码完成，LLM 只负责"判断与表达"。这样既压成本（日均 4 千 token），又把幻觉风险关在最小范围内。

## 3. 产品定义与质量红线

- **内容结构**：今日速览 → 新品发布与规格拆解 → 技术与芯片动向 → 融资与招聘信号 → 一句话点评
- **四条红线**：① 只摘要不杜撰 ② 每条必附溯源链接 ③ 两级去重 ④ ≤12 条、5 分钟读完，无大新闻就精简，**绝不凑数**
- **国内优先**：求职导向，中文源 6 + 英文源 7，华为/小米/OPPO/vivo/荣耀等国内动态优先级高于同级国际新闻，全文中文输出

## 4. 技术架构与关键决策

| 环节 | 方案 | 为什么这么做（否掉了什么） |
|---|---|---|
| 采集 | 13 个 RSS，单源失败跳过并记日志 | 否掉"全部成功才继续"：一个源挂掉不该让日报缺席 |
| 过滤 | 双层关键词：strong 决定入选资格、weak 只加分、negative 一票否决；英文整词匹配 | 单层词表放水事故（太空望远镜事件）后的重构。整词匹配解决 `soc` 命中 social 类误伤 |
| 去重 | URL 规范化（去 utm 等参数）+ 标题 2-gram Jaccard ≥ 0.6 聚类 | 否掉 embedding 相似度：需额外 API 调用、毫秒级变百毫秒级，候选池 < 300 条时不划算 |
| 摘要 | JSON Schema 约束 + temperature 0.2 + 推理模型 `reasoning_effort=low` | 推理模型默认会把输出额度花在"思考"上导致 JSON 被截断——上线首日踩过 |
| 防幻觉 | 三层闸门：输入只给已校验材料 → 输出强约束 JSON → link 必须在输入集合内否则丢弃 | 第三层实测生效：上线首日拦下模型编造的条目 |
| 成本控制 | `budget.py` 月度 token 台账，调用前查账，超阈值前主动降级 | 免费层超额是 429 拒答而非扣费，但护栏让成本可预测、可审计 |
| 可用性 | 三层降级：单源失效跳过 / LLM 不可用出有版式速览版 / 发送失败 HTML 落盘 | 情报系统的第一性指标是"不缺席"，不是"每次都完美" |
| 调度 | GitHub Actions cron，零服务器 | 否掉自建服务器与本地 crontab：无需运维，成本为零 |
| 存档 | 每日 JSON 回写仓库 | 可审计，也是周报汇总与信源健康度分析的数据源 |

**真实运行数据**（2026-08-31 实测）：候选 58 条 → 入选 9 条；LLM 单次 4,303 tokens；端到端 23.4 秒；成本 ¥0（Groq 免费层 + Actions 免费额度 + 163 SMTP）。

## 5. 已知局限与迭代计划

诚实列出，这本身就是工程成熟度的体现：

1. **RSS 是浅窗口**：IT之家仅存最新 60 条、雷峰网 20 条，新闻会被新内容挤出。计划：提高采集频率（每日 2–3 次）+ 引入搜索 API 补漏
2. **无用户反馈闭环**：计划支持邮件内编号反馈（如"2、5 有用，3 没用"），周级自动调整信源权重
3. **相关性缺乏量化评测**：计划建 50 条人工标注样本，量化"入选准确率"，替代主观判断
4. **单用户架构**：多订阅者需改造为批量/BCC 发送，并引入退订与频控

## 6. 面试 Q&A 速查

**Q：为什么不直接用现成的 RSS 阅读器，或者每天问一次 ChatGPT？**
RSS 阅读器解决的是聚合，不解决"从 58 条里挑出 9 条并按产品视角重写"；直接问 ChatGPT 则是无信源约束的自由生成，幻觉不可控且每天质量不稳定。这个项目的价值在于两者的中间地带——**用确定性代码锁定事实边界，让 LLM 只在边界内做判断与表达**。

**Q：幻觉怎么控制？**
三层：输入侧只喂已校验材料（模型看不到外部世界）、输出侧强约束 JSON Schema、校验侧 link 白名单（不在输入集合内直接丢弃）。上线首日第三层就拦下过一条编造条目。

**Q：成本多少？怎么保证不失控？**
¥0（免费层 + 零服务器）。护栏是月度 token 台账，调用前先查账，超阈值主动降级而非继续烧；且未绑信用卡，超额结果是 429 拒答不是扣费。

**Q：失败过吗？怎么处理的？**
四个真问题：① LLM 服务商（GitHub Models）官方退役 → 配置化迁移到 Groq，一行代码未改 ② 中文信源 XML 损坏 → 实测 12 个源后替换 ③ 关键词放水混入无关内容 → 重构为双层 + 黑名单 ④ 推理模型输出被截断 → 加 `reasoning_effort=low` 并扩大输出额度。每次都写进了 commit message。

**Q：如果用的人多了怎么办？**
发信改批量/BCC 并引入退订；去重从 O(n²) 换 MinHash/LSH；相关性用轻量 embedding 重排；LLM 换按量计费并保留护栏。当前规模（n<300、每天 1 次）下这些优化都是过度设计。

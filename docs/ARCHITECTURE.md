# 架构决策记录（ADR）

> 这份文档是给面试官看的：每个决策都写了"为什么"，以及被否掉的备选方案。

## D1. 采集：RSS 优先，不爬网页

- **选**：RSS（feedparser）+ 关键词打分
- **弃**：搜索引擎 API（成本高、结果不稳定）、爬虫（反爬维护成本高、法务风险）
- **理由**：主流科技媒体全部提供 RSS，结构化、稳定、免费。信源质量靠 priority 权重 + 存档数据复盘来治理，而不是靠多抓。

## D2. 去重：两级流水线，不用向量库

- **第一级** URL 规范化：去 utm 跟踪参数/fragment/大小写统一，O(n)，解决"同文不同参"；
- **第二级** 标题 2-gram Shingle + Jaccard ≥ 0.6 聚类，O(n²) 但候选池 <300 条，毫秒级；
- **弃**：embedding 相似度（需向量库/额外 API 成本，标题短文本上收益有限）与 SimHash（汉明距离对短文本粒度太粗）
- **聚类代表**：取来源权威度最高的条目，兼顾"权威来源优先"的编辑策略。

## D3. 摘要：强约束 JSON 输出 + 双向校验防幻觉

- 输入侧：只给已打分已去重的材料，prompt 显式禁止使用材料外信息；
- 输出侧：要求 JSON Schema；`_validate()` 校验每条 item 的 link **必须原样存在于输入 URL 集合**，不在即丢弃——这是防幻觉的最后闸门，也是本项目在面试中最值得讲的点；
- **弃**：自由文本输出再正则解析（脆弱、无法机器校验溯源）。

## D4. 可用性：三层降级，日报绝不缺席

```
单 RSS 源失败 → 跳过记日志（不影响整体）
LLM 失败(重试3次后) → 降级为标题+链接列表
SMTP 失败 → HTML 落盘 out/，可人工补发
```

订阅型产品的可用性定义是"每天都有一封值得打开的邮件"，而不是"每封都完美"。

## D5. 调度：GitHub Actions，零服务器

- **双通道触发**：主通道 `repository_dispatch`（方案 A 每天 10:00 发完邮件后调 GitHub API 触发，~10:15 送达）+ cron `33 3 * * *`（UTC 03:33 = 北京 11:33）兜底；
- 兜底的必要性是实测出来的：GitHub 定时任务在美西高峰时段（原 cron UTC 00:30）排队延迟达 4.5 小时——排 08:30、12:50 才跑；
- **幂等守卫**：pipeline 启动时检查当日存档是否已存在（= 邮件已发），存在则跳过，双触发绝不重复发信；workflow 另配 `concurrency` 同组取消，双保险；
- 免运维、免费额度内、天然支持 Secrets 管理；存档 JSON 随 commit 回仓库，版本化可回溯；
- **弃**：本地 crontab（机器不常开）、云函数（多一层运维面）。

## D6. 数据底座：每天一个 JSON 存档

存档结构：`{date, mode, candidates, items[], elapsed_sec}`。三个用途：
1. **周报**：按周聚合 items 生成趋势综述；
2. **信源治理**：统计各源产出量与被采纳率，支撑"连续 3 天零产出则移除"的治理规则；
3. **反馈闭环**（roadmap）：结合邮件编号反馈调整关键词权重。

## 面试预演：最可能被追问的四个问题

1. **"幻觉怎么控制？"** → D3：输入收敛 + JSON Schema + link 白名单校验，三道闸门。
2. **"去重为什么不用向量相似度？"** → D2：成本/收益分析，短文本上 Shingle+Jaccard 足够，且零外部依赖。若候选池上量（>5000），升级路径是 MinHashLSH。
3. **"系统挂了怎么办？"** → D4 三层降级 + Actions 失败告警邮件（GitHub 默认通知）。
4. **"成本多少？"** → README 成本表；日均 <¥0.05，月成本约 ¥1.5。
